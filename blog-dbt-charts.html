DBT CHARTS: YOUR DASHBOARDS JUST BECAME CODE

SAUZI TEAM dbt Labs just turned BI into a text file. Here is what that means for teams putting AI agents on their data.

BI was the last black box in the modern data stack. dbt Labs just open-sourced a way to turn it into a text file.

On September 14, dbt Labs released dbt Charts: an open-source language for building dashboards, plus a hosted platform at dbtCharts.com, now in public beta. The tagline is "Charts built for Chat." The headline is charts. The real story is who they're built for.

Everything upstream of the dashboard already lives in code. Ingestion is config. Transformation is dbt models in git. Tests run in CI. Then you hit the BI tool and it all goes dark: logic buried in click-built tiles, definitions nobody can diff, and a dashboard graveyard nobody dares clean up. dbt Charts closes that gap.

WHAT SHIPPED

The idea is simple. SQL says what data to show. A YAML wrapper says how to show it. One file holds a board's queries, charts, layout, and written commentary, with Jinja for variables and filters (the same pattern dbt users already know).

▸An open-source CLI: dct, installed from the dbt-charts package. The language, renderer, and CLI are Apache 2.0, the same license as dbt.
▸Lives next to your models: inside a dbt project, a charts/ folder sits beside models/, queries use ref(), and dct reuses your existing profiles.yml for credentials.
▸Validation in CI: dct validate checks board columns against your models. With --warehouse it runs the cheapest check each warehouse offers (a BigQuery dry run, EXPLAIN on Snowflake and Postgres) without scanning rows.
▸Impact analysis: dct impact <column> lists every board that reads a column. Renaming a field stops being a guessing game.
▸Broad warehouse support: Snowflake, BigQuery, Databricks, Redshift, Postgres, and more through dbt adapters, with DuckDB built in.
▸A hosted platform in beta: conversational analytics, a visual editor that writes back to the YAML, scheduled renders, and permissions where readers don't need a warehouse login. Free for up to 3 collaborators.

WHY "BUILT FOR CHAT" IS THE RIGHT PITCH

dbt Labs puts the problem bluntly: AI agents make an unauditable mess of dashboards. We agree, and we'd go further. The problem isn't the agent. It's the medium.

Ask an agent to build a dashboard in a click-ops BI tool and you get something that looks right and can't be reviewed. Ask it to write a YAML file and you get a pull request. You can read it, diff it, test it, and roll it back. That's the difference between an agent you supervise and an agent you hope about.

This is the same principle we build on: no black boxes. Every pipeline, model, and connection documented so you always know what's running. dbt Charts extends that principle to the last layer of the stack, the one your executives actually look at.

A few details show the team thought about how this works in practice. The CLI lints chart design, flagging things like bars too narrow to read or tables with too many columns. Query results are cached, so fifty people opening the same board run one query, not fifty. And the pricing page promises no per-query or per-row charges on the platform. For anyone who has watched a BI bill scale with curiosity, that matters.

THE CATCH: METRICS STILL LIVE IN SQL

Here's the part worth reading twice. dbt Charts does not support the dbt Semantic Layer yet. It's on the roadmap (dbt Labs says a board will be able to use a metric "as the project defines it instead of restating its SQL"), but today every board query is SQL.

That means an agent writing boards is also writing its own definition of revenue. And active customers. And churn. Give it a messy warehouse and it will produce clean, version-controlled, beautifully linted dashboards that disagree with each other.

Code-based dashboards make bad definitions reviewable. They don’t make them correct. That job still belongs to the layer underneath: dimension and fact tables that tell the agent what a customer, an order, or a subscription actually is. Structure is the step everyone skips, and it's the step this release depends on most.

It's also worth remembering where this sits. dbt Charts is in beta and pre-1.0, and the public repo is a read-only mirror, so issues are welcome but outside pull requests are not. Expect things to move.

WHAT WE'D DO THIS WEEK

If you already run dbt, this is cheap to try and the downside is small:

▸Pick one board, not ten: rebuild a dashboard your team relies on as a dbt Charts file and see whether the YAML is easier to reason about than what you have.
▸Point it at marts, not staging: boards should read from modeled, tested tables where the business logic already lives. Keep the SQL in the board thin.
▸Wire validation into CI: dbt parse && dct validate charts/ catches a broken column before a stakeholder does.
▸Keep definitions in one place: until Semantic Layer support lands, put metric logic in your dbt models so every board (and every agent) reads the same answer.

If you're not on dbt yet, the lesson is the same. The tools for letting agents build analytics are arriving fast. The foundation they need underneath is not arriving on its own.

dbt Labs says they hope dbt Charts becomes the open standard for its layer of the stack, the way dbt did for transformation. It might. The question for your team is simpler: when an agent writes your next dashboard, will it be reading from definitions you trust?
